01 — System Overview

What the System Does

The Face Attendance System is a fully automated biometric attendance platform that eliminates proxy attendance through live facial verification. It is embedded directly inside the Zoho Creator application as a widget — no separate app to install — and records attendance with GPS location, a live-captured photo, timestamp, and check-in/check-out status.

Zero proxy attendance

Multi-layer liveness detection prevents attendance using printed photos, phone screens, or recordings.

Instant recording

Attendance is queued within milliseconds of face recognition. The Zoho Creator record appears within seconds even under slow network conditions.

GPS-verified location

The trainee's device GPS coordinates are captured at check-in and check-out and stored with every attendance record.

Live photo audit trail

The actual camera frame used to verify the trainee is attached to the Zoho Creator attendance record as an audit photograph.

Native Zoho integration

Built as a Zoho Creator Widget using the official SDK v2. No data leaves the system boundary; attendance records are created directly in Creator.

Self-improving accuracy

Every successful verified check-in stores an updated face embedding, so the model adapts to lighting, ageing, and appearance changes over time.

03 — AI Models

Artificial Intelligence Components

The system uses five distinct AI models operating at different layers of the verification pipeline. Each model has a specific, non-overlapping role; together they form a defence-in-depth architecture that balances accuracy, speed, and spoof resistance.

1. InsightFace buffalo_l — Face Embedding Model

Role: face detection + embedding extraction (server-side)

This is the primary identification model. It detects the face in a submitted frame, extracts a 512-dimensional numerical fingerprint called an embedding, and that fingerprint is compared against stored enrollment embeddings to identify the trainee.

ArchitectureResNet100 backbone trained with ArcFace loss (angular margin classification)
Face detectorRetinaFace (included in buffalo_l model pack)
Embedding size512 floating-point values, L2-normalised to unit length
Detection grid320 × 320 px (reduced from 640 to fit within 2 GB RAM limit on hosted server)
Similarity metricCosine similarity (dot product of two normalised vectors, range −1 to 1)
Inference engineONNX Runtime, CPU provider (no GPU required)
Model size on disk~350 MB (loaded once at server start, shared across workers)
Thread safetySerialised with a per-process inference lock (ONNX session state is not thread-safe)

2. MiniFASNetV2 — Local Passive Anti-Spoofing

Role: spoof detection before face matching (server-side, free, instant)

This model examines the submitted frame and determines whether the face is physically present (live) or is a spoof artifact — a printed photo, phone screen, mask, or video replay. It runs before any identity matching occurs.

ArchitectureMiniFASNetV2 — lightweight ONNX model (~1.0 MB)
Inference typePassive (single frame, no user action required)
InputFace crop expanded 2.7× from detected bounding box, resized to 80 × 80 px
OutputSoftmax probability: index 1 = real-face probability (0.0 – 1.0)
Threshold0.65 — frames below this are flagged as suspected spoofs
Fail-open behaviourIf model file is unavailable (development environment), the check is skipped gracefully

3. AWS Rekognition DetectFaces — Cloud Quality Check

Role: secondary image-quality and liveness override (cloud, escalation path)

When the local MiniFASNet model suspects a spoof but is not certain (confidence near the threshold), the frame is sent to AWS Rekognition as a second opinion. AWS analyses the face's sharpness, brightness, and detection confidence — if all three metrics meet the minimum thresholds, it overrides the local model's rejection and allows the check-in to proceed.

APIAWS Rekognition DetectFaces with DEFAULT attributes
Regionap-south-1 (Mumbai)
Override conditionsDetection confidence ≥ 90.0 AND sharpness ≥ 40.0 AND brightness ≥ 15.0
Timeouts5 s connect, 8 s read, max 1 retry
Fail-safeIf AWS is unavailable, the local MiniFASNet decision stands (conservative fallback)

4. AWS Amplify FaceLivenessDetector — Interactive Oval Challenge

Role: active liveness verification for high-risk cases (browser-side + cloud)

For trainees with a prior spoof flag in their daily record, the system skips passive checks entirely and presents an AWS Face Liveness oval challenge: the trainee must align their face within a moving oval on screen. This active challenge is the strongest anti-spoofing layer and cannot be defeated by a static photo or screen recording.

TriggerTrainee has a prior spoof detection recorded for today, or MiniFASNet fails and AWS quality check also fails
FlowBrowser requests session via /api/face-liveness/create-session → AWS session ID returned → Amplify component runs oval challenge in browser → session validated server-side
ValidationSession result verified by the backend calling the AWS Face Liveness API; confidence score returned

5. MediaPipe Face Mesh — Browser-Side Liveness Challenge

Role: front-of-queue liveness challenge before the frame is sent to the server (browser-side, free)

Before any image is sent to the server, the browser uses MediaPipe's real-time face landmark model to verify that a live face is present by detecting a voluntary physical action — a blink or a smile. This eliminates simple spoofs at the client level before consuming any server or API resources.

ModelMediaPipe Face Mesh v0.4 — 468 facial landmarks per frame
ConfigurationmaxNumFaces = 1, refineLandmarks = true, minDetectionConfidence = 0.5
Blink detectionEye Aspect Ratio (EAR) computed from 6 landmarks per eye; exponential smoothing (α = 0.3); thresholds: close EAR < 0.22, open EAR > 0.27; 1 complete blink required
Smile detectionMouth width-to-height ratio threshold 0.7; 3 consecutive frames required
Auto-switchIf the trainee has not completed the challenge within 15 seconds, the system alternates between blink and smile prompts automatically

04 — End-to-End Flow

How a Check-In Works — Step by Step

The complete attendance flow from widget load to Zoho Creator record creation. Each step is designed to be resilient: if any layer fails, the system falls back gracefully rather than blocking the trainee or losing data.

1

Widget Loads in Zoho Creator

The Face Attendance widget loads inside the trainer's or centre manager's Zoho Creator application page. The Zoho Creator Widget SDK v2 identifies the logged-in user (email address), which determines which centres they manage and which students to load.

2

GPS Permission & Location Capture

The widget requests the device's GPS location via the browser Geolocation API. A full-screen gate blocks the app until permission is granted and coordinates are obtained (high accuracy, max 30 s timeout). The coordinates are stored in browser memory and will be attached to every attendance record submitted from this session.

3

Session Authentication

The browser exchanges the user's email and Zoho environment for a 30-minute HMAC-SHA256 Bearer token from the backend (/api/session). Every subsequent API call carries this token; expired tokens are automatically re-issued once without interrupting the user.

4

Student Data Loading

The widget loads the list of enrolled trainees via a hybrid strategy: it first queries Zoho Creator directly via the Widget SDK (fastest, no server round-trip), then falls back to the backend's cached student list at /api/preload if the SDK query is insufficient. The backend caches embeddings for 24 hours in its local PostgreSQL database, refreshing only stale or missing entries from Zoho.

5

Browser Liveness Challenge (MediaPipe)

The trainee faces the camera. MediaPipe Face Mesh tracks 468 facial landmarks in real time. The system randomly requires either a blink or a smile — a voluntary movement that proves the face is live and physically present, not a photo or screen. The challenge automatically switches if not completed within 15 seconds.

6

Frame Capture & Server Submission

On completing the browser liveness challenge, the frame is captured from the canvas as a JPEG and sent as a base64-encoded payload to /api/verify along with the GPS coordinates and device session ID. The request is authenticated with the Bearer token.

7

Server-Side Liveness Check (MiniFASNet)

The server decodes the image, detects the face bounding box, and passes the face crop to the MiniFASNetV2 ONNX model for passive anti-spoofing analysis. If the real-face probability is below 0.65, the frame is flagged as a suspected spoof. Depending on whether a prior spoof flag exists for this trainee today, the system either: (a) escalates to AWS Rekognition for a quality override check, or (b) triggers the AWS Face Liveness oval challenge in the browser.

8

Face Embedding Matching

If liveness checks pass, the InsightFace buffalo_l model extracts a 512-dimensional embedding from the frame. This is compared against stored embeddings for all trainees in the loaded scope using cosine similarity. The trainee with the highest mean similarity across their top-2 stored embeddings is selected — provided their score exceeds the 0.50 tolerance threshold AND they beat the nearest other trainee by at least 0.08 margin.

9

Self-Learning Embedding Update

If the match confidence is 70% or above, the live-capture embedding is stored as a new verified reference embedding for that trainee (cycling through verified_1, verified_2, verified_3 slots). Future matches will use this updated embedding, adapting to lighting, appearance, and angle changes over time.

10

Attendance Queued Instantly

The matched trainee's check-in is recorded immediately to the local PostgreSQL outbox queue. Three deduplication layers (in-memory set, database count check, and UNIQUE constraint) ensure exactly-once recording even under concurrent requests or network retries. The trainee sees a success confirmation in under 2 seconds regardless of Zoho API latency.

11

Background Worker Posts to Zoho Creator

A background worker drains the queue and POSTs each attendance record to the Zoho Creator Attendance form via the REST API v2. The record includes: trainee lookup, date, check-in time (IST), attendance status (Present), zone, centre, batch, GPS coordinates (latitude/longitude), source identifier ("Face Recognition"), and the live-captured JPEG photograph. Failed posts retry up to 5 times with exponential backoff (5 s → 15 s → 45 s → 135 s → 405 s).

12

Live Photo Attached to Zoho Record

After the attendance record is created in Zoho Creator, the backend patches the record with the live-capture JPEG, uploading it to the designated image field (Live_Captured_Image). This provides an auditable photograph of the trainee at the moment of check-in.

05 — Face Matching

How Face Verification Works

The face matching algorithm is designed to be both accurate and robust against false positives. It uses cosine similarity of ArcFace embeddings with two independent acceptance criteria — absolute score and competitive margin — both of which must pass simultaneously.

Embedding Storage

Each trainee can have up to four stored face embeddings in the system's local database:

SlotSourceWhen Created
enrollmentEnrollment photo from Zoho CreatorWhen the student record is first loaded from Zoho
verified_1Live camera capture at check-inFirst successful check-in with ≥ 70% confidence
verified_2Live camera capture at check-inSecond successful high-confidence check-in
verified_3Live camera capture at check-inThird successful high-confidence check-in (oldest slot recycled)

Matching Algorithm

When a face is submitted for verification, the following process runs in sequence:

1

Build embedding matrix

All stored embeddings for all in-scope trainees are assembled into a matrix. A trainee with 4 stored embeddings contributes 4 rows; one with only an enrollment photo contributes 1 row.

2

Compute cosine similarities

The submitted embedding (512-d unit vector) is dot-producted against every row of the matrix in a single NumPy operation. Because both vectors are L2-normalised, the dot product equals cosine similarity, ranging from −1 (opposite) to 1 (identical).

3

Per-student score (Top-2 mean)

For each trainee, the top-2 highest similarities across their stored embeddings are averaged. This prevents a single weak or incorrectly-learned embedding from carrying a false match — it must perform consistently across the two best embeddings.

4

Two-gate acceptance check

The top-scoring trainee passes only if: (a) Absolute threshold: their score ≥ 0.50, AND (b) Margin check: their score beats the second-highest trainee by at least 0.08. If the match is ambiguous (two trainees score similarly), it is rejected and the trainee is asked to retry — this prevents misidentification in group settings.

Configurable Thresholds

ParameterDefaultRangeDescription
Match tolerance 0.50 0.20 – 0.80 Minimum cosine similarity to accept a match. Higher values are stricter.
Minimum margin 0.08 0.0 – 0.30 Winner must beat runner-up by at least this amount to prevent ambiguous matches.
Top-K embeddings 2 1 – 5 Number of best embeddings per student averaged into the final score.
Verified embedding min confidence 70% 0 – 99.9% Minimum match confidence for a live-capture embedding to be stored as a verified reference.

Confidence Score

When a match is accepted, a 0–100% confidence score is calculated and displayed to the operator. The score is derived as: (best_score − tolerance) / (0.75 − tolerance) × 100, capped at 99.9%. A score of 70%+ is required before a live-capture frame is stored as a future reference embedding.

Enrollment Photo Handling

Enrollment photos are downloaded from Zoho Creator and encoded using the same InsightFace model. The system handles several edge cases automatically:

  • HEIC / HEIF format (iPhone photos) decoded via pillow-heif
  • EXIF orientation correction applied before encoding
  • Automatic 90°, 180°, 270° rotation fallbacks for photos with missing or incorrect EXIF data
  • Large images (over 1920 px) downsampled before processing to prevent out-of-memory errors on the 2 GB server

06 — Anti-Spoofing

Multi-Layer Liveness Detection

The system uses four independent liveness layers arranged in a decision tree. Layers 1 and 2 are always active for every check-in; layers 3 and 4 are triggered only on escalation. This design minimises API costs and latency for legitimate trainees while providing the strongest available protection against spoofing.

👁

Layer 1 — MediaPipe Blink / Smile Challenge (browser)

Runs in the browser before the frame leaves the device. Proves a live face is physically present by requiring a voluntary blink or smile, defeating static photos and passive video replays.

🛡

Layer 2 — MiniFASNetV2 Passive Anti-Spoofing (server)

Every submitted frame is analysed by an on-server ONNX model for spoof artifacts (texture, moiré patterns, screen reflections). Runs in < 50 ms. No API cost.

☁

Layer 3 — AWS Rekognition Quality Override (cloud, escalation)

Triggered when Layer 2 is uncertain. AWS independently assesses detection confidence, sharpness, and brightness. If all three exceed minimum thresholds, it overrides the local rejection — preventing false positives in difficult lighting.

🔵

Layer 4 — AWS Amplify Face Liveness Oval Challenge (interactive, highest assurance)

Triggered for trainees with a prior spoof flag today, or when both Layers 2 and 3 fail. The trainee must align their face within a moving oval on screen — an active biometric challenge that cannot be defeated by any static or recorded media.

Spoof History Tracking

The system maintains a daily spoof attempt log (spoof_attempts table) and a spoof block table (spoof_blocks). A trainee whose device has triggered a spoof detection today is automatically escalated to Layer 4 for all subsequent check-in attempts that day, bypassing the lighter checks.

07 — GPS & Geolocation

Location Verification

Every attendance record is paired with GPS coordinates captured from the trainee's device at the moment of check-in and check-out. This creates an auditable location trail for each attendance event, enabling centre-level proximity verification within Zoho Creator.

How Location is Captured

1

GPS gate on widget load

When the widget first loads, a full-screen overlay blocks the app and requests browser Geolocation permission (navigator.geolocation.getCurrentPosition). The request uses enableHighAccuracy: true and a 30-second timeout. The widget does not proceed until a valid position is obtained.

2

Coordinates held in browser memory

The latitude and longitude are stored in JavaScript state (_gpsState.lat, _gpsState.lng) for the duration of the session. If location is denied, a "GPS required" error screen is shown and the app remains blocked.

3

Coordinates sent with every attendance record

At check-in and again at check-out, the coordinates are included in the POST payload sent to /api/post-attendance. The backend stores them in the local queue and forwards them to Zoho Creator in the attendance record.

4

Stored as four fields in Zoho Creator

The Zoho Creator Attendance form has four dedicated fields: Checkin_Latitude, Checkin_Longitude, Checkout_Latitude, and Checkout_Longitude. These are populated by the backend for every record.

Distance Calculation & Proximity Verification

How it works: The GPS coordinates captured from the trainee's device are stored verbatim in the Zoho Creator attendance record. The centre's assigned latitude and longitude are stored in the Zoho Creator Centres record. Distance calculation — computing the gap between the trainee's location and the centre location, and enforcing any proximity policy — is performed by Zoho Creator workflows and Deluge functions that compare these field values. This architecture keeps geofencing rules inside Zoho Creator where they can be updated by the operations team without code changes.

Zoho Creator Integration

The backend authenticates to Zoho Creator via OAuth2 refresh token flow. The access token is cached with a 90-second pre-expiry buffer and refreshed thread-safely. All API calls target Zoho Creator REST API v2 and are scoped to the configured application.

Student data fetch strategy

3-layer filtering: (1) server-side Zoho criteria by batch IDs; (2) Python-side batch filter as a safety net; (3) Python-side centre filter as fallback for environments where batch traversal returns 404.

Multi-centre scoping

Students and batches are loaded only for the centres assigned to the logged-in Zoho user. Scope keys (C:{id1},{id2}) ensure complete cache isolation between centre managers.

Outbox retry schedule

Failed Zoho API posts retry at 5 s, 15 s, 45 s, 135 s, and 405 s (×3 exponential backoff), up to 5 attempts. After 5 failures the record is marked FAILED and surfaced in the admin panel.

Webhook gap-fill

Zoho Creator webhooks notify the backend when new students enrol. The backend fetches only the specific new students (by ID, in chunks of 20) and adds their embeddings to the local cache without a full refresh.

10 — Security & Privacy

Security Architecture

Authentication & Authorization

Session tokens

30-minute HMAC-SHA256 Bearer tokens issued per user. Auto-renewed once on 401 without user interruption. Admin panel uses separate cookie auth.

Zoho OAuth2

Refresh token flow with thread-safe access token caching and 90-second pre-expiry buffer. Credentials stored as environment variables on Render, never in code.

CORS policy

API accepts requests only from Zoho Creator domains, the Render service URL, and localhost for development. All other origins are rejected at the network layer.

Rate limiting

120 req/min global, 60 req/min on attendance posting, 20 req/min on webhooks. Protects against brute-force and denial-of-service attempts.

Biometric Data Handling

Face embeddings are mathematical abstractions, not photographs. The 512-dimensional vectors stored in the database cannot be reverse-engineered into a face image. The raw enrollment photographs from Zoho Creator are processed in memory and then discarded — only the numerical embeddings are persisted locally. Live-capture JPEGs are held only long enough to upload to the Zoho Creator record and are not stored permanently on the backend.

Infrastructure Security

  • All traffic served over TLS (HTTPS) via Render's managed edge
  • No secrets in source code — all credentials loaded from environment variables
  • Server refuses to start if SECRET_KEY or ADMIN_SECRET are left at default values in production
  • 5 MB maximum request body — prevents memory exhaustion via oversized uploads
  • ONNX inference serialised per process — no race conditions in concurrent workers
